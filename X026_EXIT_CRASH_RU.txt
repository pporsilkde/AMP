0. ВАЖНО: присланное дерево AMP.zip — это X024, БЕЗ X025
======================================================================

В AMP.zip лежит hud.cpp/hud.hpp ровно того же содержимого, что ты присылал
в X024-архиве (sha256 совпадают байт в байт):

  apps/openmw/mwgui/hud.cpp  3c74fad855ee973d0132abc9dc87c61919a1554d…
  apps/openmw/mwgui/hud.hpp  bae6d2ce72cdbab50a4eabfb897b8d235035d938…

Полосок X025 (стопка над стаминой) там нет. То есть либо ты прислал дерево
до наложения X025, либо X025 не наложен вообще. К этому крашу X025
отношения не имеет — падение целиком в X022-логике, см. ниже. X025 на это
дерево по-прежнему ложится без конфликтов.


======================================================================
1. Что показал дамп
======================================================================

Разобрал tes3mp-client_log-crash.dmp напрямую (это minidump, тип 0x5:
data segments + handles; полного хипа в нём нет, но есть 256 байт кода
вокруг точки падения и .data всех модулей — этого хватило).

  Исключение: 0xC0000005, ACCESS_VIOLATION на ЧТЕНИЕ по адресу 0x0000000000000018
  Поток:      13100
  RIP:        tes3mp.exe+0x1414AB
  RCX:        0x0000000000000000

Дизассемблировал сохранённые байты кода:

  ...
  lea  rdx,[rip+0x8e93]              ; адрес метода
  mov  rcx,r14                       ; this
  call 0x7ff719228800                ; MyGUI::newDelegate(this, &Метод)
  mov  rdi,rax                       ; временный делегат (0x58 байт)
  mov  rcx,QWORD PTR [rip+0x93db25]  ; ГЛОБАЛ  ->  0x0000000000000000
  mov  rsi,QWORD PTR [rcx+0x18]      ; <<< ПАДЕНИЕ, чтение по 0x18
  ...
  далее обход std::list делегатов, сравнение по +0x48 и +0x50,
  затем operator delete(rdi, 0x58)

Это дословно раскрытый оператор `event -= MyGUI::newDelegate(...)`.
Глобал, который равен нулю, — это mwmp::Main::pMain.
Смещение 0x18 в классе Main — это ровно mGUIController:

  Networking     *mNetworking;      // 0x00
  LocalSystem    *mLocalSystem;     // 0x08
  LocalPlayer    *mLocalPlayer;     // 0x10
  GUIController  *mGUIController;   // 0x18   <-- адрес падения
  CellController *mCellController;  // 0x20

Причём непосредственно перед упавшим блоком в коде стоит точно такой же
блок, отработавший успешно. Это две подряд идущие строки одного и того же
деструктора.


======================================================================
2. Где именно
======================================================================

apps/openmw/mwgui/mapwindow.cpp, LocalMapBase::~LocalMapBase():

    mCustomMarkers.eventMarkersChanged -= MyGUI::newDelegate(...);          // отработало
    mwmp::Main::get().getGUIController()->mPlayerMarkers
        .eventMarkersChanged -= MyGUI::newDelegate(...);                    // упало

Main::get() — это просто `return *pMain;`, а Main::destroy() делает
`delete pMain; pMain = 0;`. То есть getGUIController() вызывается на нулевом
this и читает поле по смещению 0x18.

Цепочка вызовов на выходе:

  OMW::Engine::~Engine()
    -> mwmp::Main::destroy()            // X022: pMain становится nullptr
    -> mEnvironment.cleanup()
         -> WindowManager::~WindowManager()
              -> for (WindowBase* w : mWindows) delete w;
                   -> ~MapWindow() / ~HUD()
                        -> ~LocalMapBase()   // <<< обращение к мёртвому Main

Обрати внимание: LocalMapBase — база сразу у двух окон (MapWindow и HUD),
так что до этого места доходит гарантированно.

Почему это появилось. X022 специально перенёс mwmp::Main::destroy() ВПЕРЁД
mEnvironment.cleanup() — чтобы деструкторы DedicatedPlayer ещё видели живой
World (иначе был краш уже после строчки "tes3mp stopped" в логе). Правка
верная, но она создала зеркальную зависимость: mwmp хочет умирать при живом
World, а GUI хочет умирать при живом mwmp. Порядком это не решается — цикл.
Поэтому чинить надо на стороне GUI.

try/catch в WindowManager::~WindowManager() тут не спасает: он ловит только
MyGUI::Exception, а не аппаратное исключение.


======================================================================
3. Что сделано
======================================================================

В mapwindow.cpp добавлен один хелпер в анонимном namespace:

    mwmp::GUIController* multiplayerGuiController()
    {
        if (!mwmp::Main::isInitialized())
            return nullptr;
        return mwmp::Main::get().getGUIController();
    }

и через него теперь идут ВСЕ четыре обращения к мультиплеерному
GUIController в этом файле:

  LocalMapBase::LocalMapBase()     подписка   на mPlayerMarkers
  LocalMapBase::~LocalMapBase()    отписка    от mPlayerMarkers   <-- краш
  LocalMapBase::updatePlayerMarkers()
  MapWindow::updatePlayerMarkers()

Пропустить отписку — не костыль, а единственно правильное поведение:
если mwmp::Main уже удалён, то и коллекция mPlayerMarkers, на которую был
подписан делегат, удалена вместе с ним. Отписываться не от чего.

Подписку в конструкторе тоже завернул — симметрично, и заодно закрывает
случай запуска без успешного Main::init().

  ~EnchantingDialog, ~MessageBoxManager (и MessageBoxManager::clear),
  ~BindingsManager, ~GlobalMap, ~Scene, ~HUD, ~MapWindow,

Единственное место было в ~LocalMapBase. Оно и починено.

В Engine::~Engine() вызов mwmp::Main::get().getGUIController()->cleanUp()
уже стоит под mwmp::Main::isInitialized() — там всё в порядке.
