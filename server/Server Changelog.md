# Server Changelog — ArenaMP

## C17 — Native XP Leveling / Protocol 807 (25 августа 2026)

- Полностью заменена органическая ванильная прокачка игрока на XP + Skill Points.
- XP выдаётся из реальных игровых событий без таблиц ID: использование навыков, убийства, этапы/завершение квестов, исследование и книги.
- XP за убийство корректно доходит до реального убийцы даже когда authority умершего NPC принадлежит другому клиенту.
- Уровень повышается сразу по XP; сон и `LPRO` больше не открывают ванильный выбор x2–x5.
- Баланс `[XP Leveling]` принудительно задаётся сервером через `server/scripts/config.lua`.
- `PLAYER_LEVEL` синхронизирует XP, SP и скрытый прогресс атрибутов; список ключей одноразовых наград передаётся только при изменении, а сервер сохраняет и подтверждает состояние.
- При смерти сервер отнимает долю XP только внутри текущего уровня; уровень и Skill Points не теряются.
- Протокол повышен с 806 до 807; клиент и сервер C17 обязательны одновременно.

**Базовая сборка:** `ArenaMP(5)`  
**Тип поставки:** кумулятивный патч замены файлов  
**Дата:** 27 июля 2026 года

## 1. Система Friendly Fire

Добавлена единая политика урона между сетевыми игроками. Настройка находится в
`server/scripts/config.lua`:

```lua
config.friendlyFireMode = "group"
```

Поддерживаются три режима:

| Режим | Поведение |
|---|---|
| `disabled` | Игроки не могут наносить урон и применять вредоносные эффекты к другим игрокам. |
| `enabled` | Урон между игроками разрешён без ограничений. |
| `group` | Урон разрешён по посторонним игрокам, но блокируется между союзниками одной группы. |

Режим `group` использует существующую систему `/invite`, `/join` и `/leave`.
Проверка выполняется симметрично по спискам союзников обеих сторон.

### Какие воздействия проверяются

- рукопашные и оружейные удары;
- луки, арбалеты, метательное и другое дистанционное оружие;
- зачарования оружия и боеприпасов при попадании;
- заклинания на касание, на цель и по площади;
- отражённые вредоносные эффекты;
- паралич, урон, истощение, поглощение и другие эффекты с флагом `Harmful`;
- длительные эффекты и урон с течением времени;
- изменение режима или состава группы во время действия эффекта.

Лечение, усиления и другие невредоносные компоненты смешанных заклинаний не
блокируются. Самонацеленные эффекты разрешены.

### Уровни защиты

1. Клиент атакующего отбрасывает запрещённое попадание до расчёта урона,
   износа оружия, расхода зачарования и назначения сетевой цели.
2. Сервер очищает результат запрещённой физической атаки перед ретрансляцией:
   попадание, урон, нокдаун, блок и флаги зачарований.
3. Клиент цели повторно проверяет входящий удар до изменения здоровья и других
   последствий.
4. Магическая система проверяет каждый вредоносный эффект отдельно, включая
   площадь и отражение.
5. Кэш длительных эффектов пересобирается после изменения режима или списка
   союзников; запрещённый эффект приостанавливается, пока правило его блокирует.

### Lua API

Высокоуровневый модуль CoreScripts:

```lua
friendlyFire.GetMode()
friendlyFire.SetMode(mode, sendToPlayers)
friendlyFire.ArePlayersGrouped(firstPid, secondPid)
friendlyFire.CanDamage(attackerPid, targetPid)
```

Пример пользовательского урона:

```lua
if friendlyFire.CanDamage(attackerPid, targetPid) then
    -- Здесь применяется пользовательский урон.
end
```

Нативные функции `tes3mp`:

```lua
tes3mp.SetFriendlyFireMode(mode)
tes3mp.GetFriendlyFireMode()
tes3mp.ArePlayersAllied(firstPid, secondPid)
tes3mp.IsFriendlyFireAllowed(attackerPid, targetPid)
```

`friendlyFire.SetMode()` позволяет изменить режим во время работы сервера и по
умолчанию повторно отправляет настройки всем вошедшим игрокам.

## 2. Локальная AOI-синхронизация объектов

Контейнеры, двери и состояния объектов больше не рассылаются игрокам на другом
конце мира.

- Интерьер: пакет получают только игроки с загруженным интерьером с тем же
  точным именем, включая разделение персональных инстансов.
- Экстерьер: пакет получают игроки, у которых загружена ячейка события — текущая
  и соседняя сетка `3×3`.

Фильтрация применяется к контейнерам, дверям, состояниям, замкам, ловушкам,
созданию и удалению объектов, масштабу, перемещению, вращению, звукам,
объектным анимациям и локальным переменным скриптов.

Сервер продолжает сохранять авторитетное состояние. Игрок, вошедший позднее,
получает актуальный снимок ячейки обычным механизмом загрузки.

## 3. Надёжное отключение клиентских скриптов

После получения пустой динамической замены клиент удаляет ранее
скомпилированный байткод, кэш локальных переменных и уже работающий глобальный
экземпляр. Это устраняет выполнение старой версии, например
`CharGenDoorExitCaptain`, после её отключения сервером.

## 4. Синхронизация книг и листовок

При чтении другие игроки видят и анимацию, и модель книги, записки или листовки
в руке персонажа. Модель повторно прикрепляется после пересборки внешности и
удаляется после окончания чтения.

## 5. Настройки и совместимость

- Добавлена резервная настройка `[Game] friendly fire mode = group`.
- CoreScripts передают фактический режим через `ID_GAME_SETTINGS`.
- Поддерживаются алиасы `off/on`, `false/true`, `0/1`, `party`, `ally`, `allies`.
- Friendly Fire применяется только когда обе стороны являются сетевыми
  игроками; поведение NPC, существ и обычных спутников не изменено.
- Пользовательские Lua-механики, напрямую меняющие здоровье или характеристики,
  должны вызывать `friendlyFire.CanDamage()`.

## 6. Определение языка клиента и серверная локализация

Клиент передаёт серверу язык интерфейса ArenaMP вместе с пакетом
`ID_PLAYER_BASEINFO`. Значение вычисляется по настройке
`[General] interface language`; режим `auto` следует кодировке игровых данных.

Сервер принимает только два канонических флага:

| Флаг | Значение |
|---|---|
| `RU` | Русская локализация клиента. |
| `EN` | Английская и любая другая локализация. |

Неизвестное, пустое или подменённое значение нормализуется сервером до `EN`.
Изменение структуры `PlayerBaseInfo` сопровождается повышением версии протокола
с `805` до `806`, поэтому клиент и сервер должны быть обновлены одновременно.

### Доступ к языку из Lua

Во время подключения флаг записывается в объект игрока:

```lua
Players[pid].language -- "RU" или "EN"
```

Также доступны:

```lua
tes3mp.GetLanguage(pid)
localization.GetLanguage(pid)
localization.SetPlayerLanguage(pid, "RU") -- сессионное переопределение Lua
```

`SetPlayerLanguage()` не изменяет локальную настройку клиента и действует до
отключения игрока.

### Общий словарь серверных сообщений

Добавлен модуль:

```text
server/scripts/localization.lua
```

и основной словарь:

```text
server/scripts/locales/core.lua
```

Модуль прозрачно оборачивает `SendMessage`, `MessageBox`,
`CustomMessageBox`, `InputDialog`, `PasswordDialog` и `ListBox`. Встроенные
сообщения CoreScripts, окна входа и регистрации, системные уведомления,
сообщения групп, административные ответы, справочные меню и демонстрационное
меню ремесла отображаются на языке конкретного получателя.

На сервере со смешанными языками одно системное сообщение переводится отдельно
для каждого получателя. При одинаковом тексте для всех игроков сохраняется
обычная единичная широковещательная отправка. Для персонализированной рассылки
добавлена нативная функция:

```lua
tes3mp.SendMessageTo(sourcePid, targetPid, message)
```

Она сохраняет исходного отправителя пакета, поэтому локализация не ломает
отображение говорящего, голосовые функции и TTS.

### Подключение словаря стороннего скрипта

Сторонний модуль может зарегистрировать собственное пространство ключей:

```lua
localization.RegisterDictionary("trading", {
    EN = {
        offer = "{name} offers {count} items."
    },
    RU = {
        offer = "{name} предлагает предметов: {count}."
    }
})

local text = localization.Get(pid, "trading", "offer", {
    name = Players[sellerPid].name,
    count = itemCount
})

tes3mp.SendMessage(pid, text, false)
```

Словарь из отдельного файла подключается так:

```lua
localization.LoadDictionary("trading", "myScript.locales")
```

Дополнительно словарь может содержать секцию `automatic.RU` с таблицами
`exact`, `patterns` и `phrases`, чтобы автоматически переводить уже существующие
вызовы CoreScripts без их переписывания.

### Совместимость пользовательских скриптов

Неизвестный ключ возвращается в виде `namespace.key`, а отсутствующий русский
перевод автоматически берётся из таблицы `EN`. Неизвестный свободный текст
остаётся без изменений. Поэтому старые скрипты продолжают работать, а новые
могут постепенно подключать собственные словари.

## 7. Исправление сборки локализованного чата

Исправлена ошибка MSVC `C2065: 'player': undeclared identifier` в функции
`ChatFunctions::SendMessageTo()`.

Причиной был общий макрос `GET_PLAYER(pid, pl, retvalue)`: он записывал найденного
игрока в переданный параметр `pl`, но затем ошибочно проверял жёстко заданную
переменную `player`. Поэтому вызовы с именами `sourcePlayer`, `targetPlayer` и
`alliedPlayer` либо не компилировались, либо могли проверять не тот указатель.

Проверка исправлена с:

```cpp
if (player == 0)
```

на:

```cpp
if (pl == 0)
```

Теперь `SendMessageTo()` компилируется с двумя независимыми указателями, а все
остальные вызовы `GET_PLAYER` корректно проверяют именно тот объект, который
передан макросу.

## 2026-07-27 — Server language selector and synchronized reading props v4

- В самое начало `server/scripts/config.lua` добавлена настройка:


  ```lua
  localization.GetServerLanguage()
  localization.SetServerLanguage("AUTO")
  localization.GetClientLanguage(pid)
  localization.GetLanguage(pid)
  ```

  `GetClientLanguage()` возвращает фактический флаг клиента, а `GetLanguage()` — итоговый язык с учётом принудительной настройки сервера.

### Настройка в лаунчере

- В верхнюю часть раздела **Server Settings → General** добавлен список **Server language**.
- Варианты лаунчера: `Auto (client language)`, `Русский`, `English`.
- Загрузка формы читает `config.serverLanguage`, а сохранение безопасно изменяет только первое пользовательское присваивание в `config.lua`.

### Книги и свитки в руках игроков

- При чтении теперь используется точная модель открытого предмета как для книги, так и для свитка; универсальный пергамент применяется только как резерв для записи без модели.
- Пути моделей нормализуются к VFS-пути `meshes\\...` перед локальным прикреплением и сетевой передачей.
- Модель прикрепляется к `Bip01 R Hand` локального персонажа и удалённых игроков и восстанавливается после пересборки скелета или экипировки.
- Пока окно чтения открыто, клиент раз в 3 секунды повторно передаёт активное состояние предмета игрокам в своей AOI. Благодаря этому игроки, вошедшие в текущую/соседнюю ячейку после начала чтения, также видят книгу или свиток.
- Повторный одинаковый пакет не перезапускает анимацию на удалённом клиенте: он только восстанавливает модель и продлевает актуальность состояния.
- При закрытии книги или свитка отправляется остановка, а модель удаляется у самого игрока и у всех наблюдателей.

## macOS: исправлена упаковка среды выполнения SDL3

- Исправлен сбой запуска ArenaMP на чистых системах macOS при сборке через Homebrew `sdl2-compat`.
- В установку зависимостей добавлена явная установка и проверка ARM64-библиотеки `sdl3`, которую `sdl2-compat` использует внутри.

- Готовое приложение больше не требует установки Homebrew, `sdl3` или `sdl2-compat` на компьютере игрока.

## 2026-07-27 — macOS SDL3 loader filename and runtime-probe fix v7

- Исправлена ошибка запуска `Failed loading SDL3 library.` в Homebrew `sdl2-compat` 2.32.70.
- Причина: актуальный `sdl2-compat` на macOS вызывает `dlopen()` для имени `libSDL3.dylib`, тогда как предыдущая упаковка предоставляла только `libSDL3.0.dylib`. Статическая проверка `otool` не могла обнаружить ошибку, потому что SDL3 загружается динамически.
- Единственная реальная библиотека теперь размещается в `ArenaMP.app/Contents/Frameworks/libSDL3.dylib` с переносимым идентификатором `@rpath/libSDL3.dylib`.
- В `Contents/MacOS` создана ссылка `libSDL3.dylib`, поэтому одновременно работают поиски через `@loader_path` и `@executable_path` независимо от расположения `sdl2-compat`.
- Добавлены совместимые псевдонимы `libSDL3.0.dylib`, `libSDL3-3.0.dylib` и `libSDL3-3.0.0.dylib` для старых вариантов compatibility layer и сторонних модулей.
- Перед подписью приложения CI компилирует временный ARM64-пробник, загружает именно встроенную библиотеку SDL2 и вызывает `SDL_Init(SDL_INIT_TIMER)`. Сборка завершается ошибкой, если `sdl2-compat` не способен реально открыть встроенную SDL3.
- Проверка `.app` и DMG контролирует реальную библиотеку, её install name, ARM64 и все SDL3-псевдонимы.


## 2026-07-27 — macOS SDL3 runtime-probe SDK fix v8

- Исправлена ошибка CI `SDL_platform.h: fatal error: 'AvailabilityMacros.h' file not found`.
- Ошибка находилась не в основной сборке ArenaMP и не в библиотеке SDL3, а во временном проверочном приложении, добавленном в v7: оно подключало Homebrew-заголовок `SDL.h` при прямом запуске `clang` без явно заданного macOS SDK sysroot.
- Проверочный код больше не подключает заголовки SDL и не зависит от каталога `sdl2-compat/include/SDL2`.
- Встроенная `sdl2-compat` теперь открывается через `dlopen()`, а функции `SDL_Init`, `SDL_Quit` и `SDL_GetError` разрешаются через `dlsym()`. Таким образом проверяется именно фактическая способность упакованного compatibility layer загрузить встроенную SDL3.
- Для компиляции пробника явно задаются `xcrun --sdk macosx --show-sdk-path` и `-isysroot`, поэтому системные заголовки всегда берутся из выбранного Xcode SDK.
- Добавлена автоматическая очистка временного исходника и бинарного пробника как при успехе, так и при ошибке.
- Workflow запрещает повторное подключение Homebrew SDL-заголовков в runtime-пробнике и проверяет наличие реализации через `dlopen()`.

## 2026-07-27 — macOS dedicated-server POSIX path fix (v11)

- Исправлен аварийный выход встроенного `tes3mp-server` с сообщением `Script not found: ./server:scripts:serverCore.lua`.
- Причина находилась в `Utils::convertPath()`: на macOS все символы `/` заменялись устаревшим HFS-разделителем `:`. Современная macOS и стандартные функции `fopen()` используют POSIX-пути с `/`.
- На macOS пути теперь остаются без изменений; преобразование `/` в `\\` выполняется только в Windows.
- Исправление распространяется на загрузку `serverCore.lua`, каталог `server/data`, Lua `package.path` и пути нативных серверных модулей.
- В macOS CI добавлена отдельная проверка `check-posix-server-paths.sh`, запрещающая возвращение ветки `__APPLE__` с разделителем `:`.
- После упаковки `.app` CI запускает именно встроенный `tes3mp-server` из `Contents/Resources`, проверяет, что он загрузил серверное ядро и остаётся запущенным, после чего корректно завершает тестовый процесс.
- DMG больше не публикуется, если сервер формирует путь вида `./server:scripts:*`, сообщает `Script not found` или завершается во время инициализации.

## 2026-07-27 — macOS ARM64 RakNet ACK sentinel fix (v12)

- Исправлен повторяемый краш клиента `tes3mp` с `EXC_BREAKPOINT / SIGTRAP` в `RakNet::CCRakNetSlidingWindow::ShouldSendACKs()` сразу после запуска сетевого потока.
- Причина находилась в старом коде CrabNet/RakNet: значение `double -1.0`, обозначающее «RTT ещё не измерен», приводилось к беззнаковому `CCTimeType` (`uint64_t`). Такое преобразование отрицательного floating-point значения в беззнаковый целый тип находится вне допустимого диапазона и является неопределённым поведением C++.
- В Release-сборке Apple Clang ARM64 распознавал это неопределённое поведение и оптимизировал `ShouldSendACKs()` в безусловную инструкцию `brk #1`, что полностью совпадает с тремя приложенными crash report: одинаковый адрес, `symbolLocation: 0` и сетевой поток `RakNet::UpdateNetworkLoop`.
- Для обеих реализаций congestion control (`CCRakNetSlidingWindow` и резервной `CCRakNetUDT`) добавлен типизированный sentinel `UNSET_CC_TIME = std::numeric_limits<CCTimeType>::max()`.
- Удалены все преобразования `(CCTimeType) UNSET_TIME_US`; состояние неизвестного RTT по-прежнему означает немедленную отправку ACK, но больше не вызывает UB.
- Добавлена CI-проверка `check-raknet-ack-sentinel.sh`: она запрещает опасное преобразование, компилирует реальную `CCRakNetSlidingWindow.cpp` с `-O2` в ARM64 assembly и блокирует сборку, если `ShouldSendACKs()` снова содержит `brk`.
- Старые crash report лаунчера относятся к предыдущей упаковке `sdl2-compat` без загруженной SDL3; серверные report подтверждают ранее исправленный uncaught `runtime_error` для пути `./server:scripts/serverCore.lua`. Отдельный клиентский RakNet-крэш устранён этим патчем.

## 2026-07-27 — macOS ARM64 typed Lua API binding fix (v13)

- Новый macOS-журнал подтвердил, что компиляция, упаковка SDL3, `macdeployqt` и проверка Wizard проходят успешно; сбой происходил уже при smoke-тесте упакованного `tes3mp-server` сразу после вывода заголовка сервера.
- Причина находилась в старом универсальном диспетчере `LangLua`: сигнатура каждой серверной C++-функции стиралась, после чего функция вызывалась через вариативный указатель `R(*)(...)`. Такой вызов не сохраняет точный ABI типов (`unsigned short`, `unsigned char`, `bool`, `double`, указатели и `noexcept`) и небезопасен на Apple Silicon.
- Все 763 обычные функции Lua API теперь регистрируются через `LuaBridge::Namespace::addFunction()` с их реальными C++-сигнатурами. Специальные стековые функции `CreateTimer`, `CreateTimerEx`, `MakePublic` и `CallPublic` остаются типизированными `lua_CFunction`.
- 21 API-макрос переведён на общий X-macro `SCRIPT_API_ENTRY`, поэтому один и тот же список продолжает формировать таблицы нативных плагинов и одновременно используется для прямой регистрации Lua без ручного дублирования имён.
- В старую встроенную версию LuaBridge добавлена C++17-специализация `FuncTraits` для указателей на `noexcept`-функции. Она сохраняет точный тип указателя и повторно использует существующую типизированную обработку функций с количеством аргументов до восьми; максимальное число аргументов ArenaMP API равно семи.
- Из `LangLua.cpp` полностью удалены `LuaFunctionDispatcher`, вызовы через `FunctionEllipsis<ReturnType>` и индексированный доступ к `functionAddresses` для Lua.
- Исправлены два выражения формирования ошибок, где строковый литерал складывался с символом как указатель (`"..." + argl[index]`) вместо создания `std::string`.
- Добавлена проверка `CI/check-lua-api-bindings.sh`: она контролирует прямую регистрацию, C++17 `noexcept`-поддержку, отсутствие старого ABI-опасного диспетчера и полноту всех API-записей. Проверка подключена к общей `CI/check-server-core.sh`, поэтому выполняется в Windows, Linux и macOS jobs.
- Существующий macOS smoke-тест упакованного сервера остаётся обязательным и теперь проверяет уже исправленный типизированный путь Lua API до публикации DMG.
