# ArenaMP X057 — единый лог, автосоздание JSON, суммоны и группа

Кумулятивный патч поверх X056. Затронуто 24 файла: 16 Lua (сервер) и 8 C++ (клиент).

Патч: `X057_ARENAMP_CORE_LOG_JSON_SUMMON_PARTY_AMP.patch`
Применяется из корня дерева AMP: `patch -p1 --binary < X057_...patch`

Флаг `--binary` обязателен: `MechanicsHelper.hpp` и `PlayerList.hpp` хранятся с
переводами строк CRLF, и без него `patch` откажется от этих двух файлов.

Рядом с патчем лежат все изменённые файлы целиком — если патч по какой-то
причине не ляжет, их можно просто скопировать поверх.

---

## 1. Убраны номера патчей из логов сервера

Раньше каждый скрипт ставил свой тег, и часто вместе с номером патча, в котором
он появился:

```
[Script]: [coreChat] ArenaMP RP chat loaded (RU/EN, no book recording)
[Script]: [ServerQuest] X048 quest hand-in resync + journal injection ...
[Script]: [X031 ConfigReload] Watching .\server\scripts/config.lua
[Script]: [QuestIndex] Reusing persistent index: loaded 1305 phaseable records
[Script]: [groupHelper] X050 loaded: groups, journal/topics sync, shared XP ...
[Script]: [resetHelrer] houseHelper.lua не найден ...
```

Теперь всё это — `[ArenaMP Core]`, а номера патчей из текста сообщений убраны:

```
[Script]: [ArenaMP Core] ArenaMP RP chat loaded (RU/EN, no book recording)
[Script]: [ArenaMP Core] quest hand-in resync + journal injection ...
[Script]: [ArenaMP Core] Watching .\server\scripts/config.lua
[Script]: [ArenaMP Core] Reusing persistent index: loaded 1305 phaseable records
[Script]: [ArenaMP Core] loaded: groups, journal/topics sync, shared XP ...
[Script]: [ArenaMP Core] houseHelper.lua не найден ...
```

Заменено 74 строки в 15 файлах. Переименованы только теги, которые уходят в
**лог сервера**.

**Теги чата не тронуты.** `[RP]`, `[L]`, `[G]`, `[P]`, `[M]`, `[A]`, `[Local]`,
`[Global]`, `[Group]`, `[Admin]`, `[Owner]`, `[Mod]`, `[Chat]`, `[XP]`,
`[Ghost Mode]` уходят игроку через `tes3mp.SendMessage`, а не в лог. Если бы
скрипт заменил и их, сломалось бы отображение каналов в coreChat.

Новый модуль `server/scripts/ampCore.lua` держит это в одном месте:

```lua
ampCore.Log(enumerations.log.INFO, "сообщение")   -- [ArenaMP Core] сообщение
ampCore.LogInfo("сообщение")
ampCore.StripLegacyTag("[groupHelper] X050 loaded")  --> "loaded"
```

`StripLegacyTag` срезает один ведущий тег в скобках и голый токен вида `X050 `,
поэтому старый код, который всё ещё передаёт тег, тоже нормализуется.

## 2. JSON создаются сами, если их нет

В логе было:

```
io2.open(): io2.file.new(): Cannot open .\server\data/custom/groupHelper.json in mode "r"
```

Эту строку печатает сама библиотека io2 в stdout **до** того, как `nil` вернётся
в Lua, поэтому `pcall` вокруг `jsonInterface.load` её не глушит. Единственное
настоящее решение — сделать так, чтобы файл существовал.

`ampCore.EnsureJson(path, default, description)`:

1. Пробует `io.open` — если файл открылся, он точно есть.
2. Пробует `jsonInterface.load`.
3. Если файла нет — записывает `default` и пишет в лог
   `Created missing data file custom/groupHelper.json`.
4. Если запись не прошла — один раз пробует создать подкаталог и повторяет.
5. Если и это не вышло — работает на дефолтах в памяти и честно пишет в лог,
   что изменения не сохранятся.

**Важно про шаг 1.** Отрицательный результат `io.open` означает «не знаю», а не
«файла нет». У вас путь `C:\Users\Зэро\Desktop\...` с кириллицей, а штатный
`io` в Lua такие пути на Windows не открывает вообще — именно поэтому TES3MP и
подставляет io2. Поэтому провал `io.open` не считается доказательством
отсутствия файла, иначе `EnsureJson` затирал бы вполне живой файл.

Отдельно: если файл **есть, но не парсится**, он остаётся нетронутым, в лог
уходит ошибка, а сессия работает на дефолтах. Порченый реестр групп можно
починить руками, молча обрезанный — нельзя.

`groupHelper.json` переведён на `EnsureJson`. Для остальных файлов есть
`ampCore.RegisterDataFile(path, default, description)` — всё
зарегистрированное создаётся на `OnServerPostInit`.

## 3. Френдли фаир на сопартийцев

**Это была настоящая ошибка, а не недоделка.** В логе сервера:

```
[2026-08-31 16:45:25] [INFO]: Friendly fire mode set to group
```

Режим `group` включён, и `MechanicsFunctions::IsFriendlyFireAllowed` разрешает
его через `Player::alliedPlayers`. Но в этот список писала **только** старая
команда `/ally` (`defaultCommands.lua`). Система групп X050 туда не писала
никогда. То есть режим «не бить союзников» был включён, а списка союзников не
было — сопартийцы спокойно били друг друга.

Теперь `groupHelper` зеркалит состав группы в `data.alliedPlayers` и вызывает
`LoadAllies()` при: создании группы, принятии приглашения, выходе, роспуске,
кике, входе игрока в игру и отключении сопартийца.

Записи, добавленные системой групп, отслеживаются отдельно
(`prefs.nativeAllies`), поэтому обновление снимает ровно их и **не трогает
союзников, добавленных вручную через `/ally`**.

Отключается: `config.groupSystem["native allies"] = false`.

## 4. Суммоны: свои и сопартийцев

### Почему агрились

`MechanicsHelper::isFriendlyFireAllowed` начинался так:

```cpp
if (!attackerIsPlayer || !targetIsPlayer)
    return true;
```

Суммон — это creature, не игрок, поэтому он выпадал из правила целиком.
Хуже: `Npc::hit` и `Npc::onHit` проверку имели, а **`Creature::hit` и
`Creature::onHit` — нет**, а именно этот путь проходит атронах или клановый
страх.

Серверный `GroupHelper_SummonTick` рассылал `StopCombat` раз в 2 секунды, но это
костыль: он срабатывает уже после того, как клиент нанёс урон и записал агро.

### Что сделано

**`MechanicsHelper::getCommandingPlayer(actor)`** — новый резолвер. Возвращает
игрока, за которого воюет актёр: сам игрок для игрока, хозяин для суммона,
подчинённого существа (Command Creature/Humanoid) и последователя, пустой `Ptr`
для обычных NPC и живности.

Работает через AI-последовательность: `ObjectList.cpp` при спавне суммона
навешивает на него `AiFollow(masterPtr)`. Обходится **вся** последовательность,
а не только активный пакет, потому что при вступлении в бой сверху ложится
`AiCombat`, а связь `AiFollow` под ним остаётся живой.

**`isFriendlyFireAllowed` теперь резолвит обе стороны через хозяина.** Одно
правило закрывает четыре случая: игрок↔игрок, игрок↔суммон, суммон↔игрок,
суммон↔суммон. Если хозяин один и тот же — `false` безусловно, в любом режиме:
по своему суммону нельзя попасть никогда.

Актёр без хозяина возвращает пустой `Ptr`, вызов отдаёт `true`, и обычные NPC и
животные сохраняют штатное боевое поведение — как и раньше.

**Проверки добавлены туда, где их не было:**

| Файл | Что закрывает |
|---|---|
| `creature.cpp` → `Creature::hit` | удар суммона до броска на попадание, урона и отправки пакета |
| `creature.cpp` → `Creature::onHit` | `setAttacked`, `actorAttacked`, hit attempt id и урон |
| `mechanicsmanagerimp.cpp` → `actorAttacked` | **вся агрессия сразу**: преступление, `startCombat`, счётчик friendlyHit |
| `actors.cpp` → `engageCombat` | суммон не может сам «решить» напасть на сопартийца по проверке заметности |

Ключевой из них — `actorAttacked`. Через него проходит **любой** источник урона:
оружие, заклинания, площадные эффекты, ловушки. Гасить только урон недостаточно —
суммон всё равно останется агрессивным.

### Суммоны помогают всей группе

`getActorsSidingWith` ходит только по follow/escort-связям, поэтому суммон
«на стороне» своего хозяина и больше ничьей. Из-за этого он стоял столбом, пока
сопартийца хозяина били.

В `Actors::engageCombat` добавлен разбор союзных игроков через
`MechanicsHelper::getAlliedPlayers`:

* сопартиец обменялся ударами с целью → суммон вступает в бой и перенимает
  `hitAttemptActorId`;
* сопартиец уже дерётся с целью → суммон становится `aggressive`, дальше
  работает штатная проверка заметности.

Множество союзных игроков собирается **отдельно и только на чтение** — оно
намеренно не сливается с `allies1`, потому что `allies1` ниже по коду уходит в
`startCombat()`, а передавать туда `Ptr` игроков нельзя.

## 5. Опыт за убийства суммоном

Схема уже была почти рабочей: клиент шлёт сигнал `amp-xp|v1|kill|...`, сервер
матчит его с событием `OnActorDeath` и делит по `sameCellRecipients`.

Починено три места:

1. **Определение хозяина.** `getSummonOwnerPid` сначала смотрит обратный индекс
   `Players[pid].summons[uniqueIndex]`, который `cell/base.lua` заполняет при
   спавне. Это быстрее перебора объектов ячейки и, главное, продолжает работать
   во время передачи авторитета над ячейкой.
2. **Атрибуция на клиенте.** `playerResponsibleForKill` в `xpleveling.cpp`
   теперь дополнительно проверяет `getCommandingPlayer(attacker) == player`.
   Старая проверка через `getActorsSidingWith` возвращает пустое множество
   короткое время после смены ячейки или передачи авторитета — ровно тогда,
   когда суммон чаще всего добивает цель.
3. **Окно совпадения.** Убийство суммоном фиксирует клиент-владелец **умирающего
   актёра**, а сигнал о награде приходит с клиента **хозяина суммона** на его
   следующем пакете уровня. Это разные тики, поэтому у событий «через суммона»
   окно 20 секунд вместо 8. Обычные убийства окно не меняют.

Дальше работает штатное деление: опыт идёт хозяину, а через
`sameCellRecipients` — всем сопартийцам в той же ячейке.

Отключается: `config.groupSystem["summon kill xp"] = false`.

## Новые опции `config.groupSystem`

```lua
["native allies"] = true,                      -- п.3: группа = союзники движка
["summon kill xp"] = true,                     -- п.5: опыт за убийства суммоном
["summon xp event lifetime seconds"] = 20,     -- п.5: окно матчинга
```

Все три можно править на лету — `configHotReload` их подхватит.

## Что НЕ вошло и почему

**Убийство суммоном в чужой ячейке.** Если ваш суммон добивает цель в ячейке,
авторитетом над которой владеет другой клиент, ваш клиент смерти не видит и
сигнал о награде не шлёт. Опыт не начислится. Это ограничение модели атрибуции
самого TES3MP, а не этого патча. Закрыть его на сервере можно было бы только
выдумав размер награды — сервер не парсит ESM и не знает уровень жертвы.
Придумывать числа я не стал.

**C++ здесь не собирался.** Проверено только структурно (баланс скобок против
базового дерева). Все 59 серверных Lua-скриптов прошли проверку структуры
блоков. Сам патч проверен по-настоящему: применён на чистое дерево и даёт
побайтово идентичный результат.

**Каталог `components/` отсутствовал в присланном AMP.zip**, поэтому в нём
ничего не менялось. Изменения этого патча в него и не лезут.

## Порядок обновления

1. Применить патч (или скопировать 24 файла).
2. Пересобрать клиент — без этого работают только серверные пункты 1, 2, 3, 5.
3. `server/scripts/ampCore.lua` — новый файл, он должен попасть в `server/scripts/`.
4. `serverCore.lua` подключает его строкой `ampCore = require("ampCore")` сразу
   после `customCommandHooks` — порядок важен, `ampCore` требует уже выбранную
   io-библиотеку в `jsonInterface` и `customEventHooks`.

## Как проверить

* В логе больше нет `X0NN` и модульных тегов — только `[ArenaMP Core]`.
* Первый старт после патча: `[ArenaMP Core] Created missing data file
  custom/groupHelper.json`, строки `io2.open(): ... Cannot open` больше нет.
* Собрать группу, ударить сопартийца — урона нет.
* Призвать атронаха, ударить его самому и попросить сопартийца — урона и агро
  нет, атронах на вас не переключается.
* Атронах бьёт врага, который напал на сопартийца, — вступает в бой.
* Убийство атронахом даёт опыт хозяину, а в группе делится по ячейке.
