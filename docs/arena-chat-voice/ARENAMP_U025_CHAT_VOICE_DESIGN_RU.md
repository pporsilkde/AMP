# ArenaMP U025 — чат и голос в лаунчере, без веба и без RakNet

Проектный документ + скелет кода. База: U024h (`MP/` + `Android/`).

Принятые решения:

| Вопрос | Решение |
|---|---|
| Транспорт голоса | Свой UDP-порт (игровой + 1), Opus, маршрутизация в процессе `tes3mp-server` |
| Транспорт чата | Свой TCP-порт (игровой + 2), постоянное соединение, пуш без опроса |
| Аккаунт | Только игровой аккаунт сервера; пароль по сети не идёт |
| Веб-обвязка | Нет. Ни PHP, ни внешней БД, ни HTTP |
| RakNet | Не трогаем: игровой протокол 806 остаётся как есть |

Три следствия, на которых держится вся конструкция:

1. **Лаунчер уже умеет OpenAL.** Коммутатор не тащит новый аудио-стек:
   источники ставятся как 3D-source, дистанция, панорама и HRTF считаются
   самим OpenAL Soft (`hrtf enable` в `settings-default.cfg` уже есть).
2. **Игровой сервер уже знает позиции всех игроков.** Голосовой маршрутизатор
   не нужен отдельным процессом — он поток внутри `tes3mp-server` и берёт
   координаты напрямую из `Players`.
3. **Сервер уже знает аккаунты, уровни и цвета.** Значит и чату не нужна
   никакая внешняя база: он живёт там же, где данные.

## 1. Топология и порты

```
        ┌─────────────────────── tes3mp-server (один процесс) ────────────────────────┐
        │                                                                             │
        │  RakNet        25565/UDP   игровой трафик — НЕ ТРОГАЕМ, протокол 806        │
        │  ArenaVoice    25566/UDP   поток VoiceServer: маршрутизация + gain/азимут   │
        │  ArenaLink     25567/TCP   поток LinkServer: вход, каналы, история, тикеты  │
        │                                                                             │
        │  хранилище чата: server/data/chat/<канал>.jsonl + кольцо в памяти           │
        └──────┬──────────────────────────┬───────────────────────────┬───────────────┘
               │ игра                     │ голос (UDP)               │ чат (TCP, постоянный)
               │                          │                           │
   ┌───────────┴────────┐      ┌──────────┴───────────────────────────┴──────────────┐
   │ КЛИЕНТ (openmw)    │      │            ЛАУНЧЕР                                   │
   │ VoiceBridge:       │ 127.0.0.1  │  VoiceCommutator   захват/Opus/OpenAL/джиттер  │
   │  позиция, поворот, ├──────┤  ArenaLinkClient   страница «Чат и голос»            │
   │  ячейка, PTT       │ UDP  │  VoicePanel        устройства, PTT, громкость, mute  │
   │ HUD: кто говорит   │◄─────┤                                                      │
   └────────────────────┘      └──────────────────────────────────────────────────────┘
```

Порты по умолчанию, все настраиваются:

```
game   = 25565/UDP     RakNet, без изменений
voice  = game + 1      (25566/UDP)   свой сокет, свой поток
link   = game + 2      (25567/TCP)   свой сокет, свой поток
bridge = 127.0.0.1:0   эфемерный, лаунчер выбирает и пишет в клиентский cfg
```

Три независимых сокета — это и есть смысл затеи: чат может отвалиться,
обновиться или быть выключен, а игра этого не заметит. Ни один новый байт
не идёт через RakNet, версия игрового протокола не меняется, старый клиент
подключается к новому серверу как раньше.

Android: те же роли в одном APK — `MainActivity`/`ChatActivity` (чат),
`VoiceService` (коммутатор, foreground service), `GameActivity` (движок).
Мост сервис↔движок — тот же loopback-UDP, что на ПК, поэтому C++ сторона
о платформе ничего не знает.

## 2. Часть A — страница «Чат и голос» в лаунчере

### A1. Навигация

`maindialog.cpp`:

* `sNavigationItems` 4 → 5 (константа участвует в расчёте ширины ячейки
  тулбара — ширина пересчитается сама).
* `createIcons()` — пятый `QListWidgetItem`, иконка `chat` в
  `components/misc/arenaicons.qrc`.
* `createPages()` — `mChatPage = new ChatPage(mLauncherSettings, this);`
  и `pagesWidget->addWidget(mChatPage)` **пятым**: порядок иконок и страниц
  обязан совпадать, `changePage()` работает по индексу строки.
* `mChatPage->setServerEndpoint(addr, port)` там же, где Play-страница
  получает адрес; при смене сервера — заново.
* `CMakeLists.txt` — `chatpage.cpp`, `arenalinkclient.cpp`,
  `voice/voicepanel.cpp`, `voice/voicecommutator.cpp` в `LAUNCHER`,
  заголовки в `LAUNCHER_HEADER` и **в `LAUNCHER_HEADER_MOC`** (все с `Q_OBJECT`).
  `Qt5::Network` уже подключён; новых зависимостей для чата нет вообще.

### A2. Вход: пароль не уходит по сети

```
  Лаунчер                                     ArenaLink (в tes3mp-server)
     │  TCP connect 25567                               │
     ├─────────────────────────────────────────────────►│
     │  HELLO {protocol, вид клиента, версия}           │
     ├─────────────────────────────────────────────────►│
     │                       CHALLENGE {nonce[16], mode}│
     │◄─────────────────────────────────────────────────┤
     │  AUTH {имя, mode, proof[32]}                     │  proof = HMAC-SHA256(
     ├─────────────────────────────────────────────────►│    sha256(пароль), nonce)
     │                                                  │  сверяется с учёткой
     │      AUTH_OK {uid, имя, уровень, цвет, класс,    │  через тот же скриптовый
     │               порт голоса}                       │  слой, что и вход в игру
     │◄─────────────────────────────────────────────────┤
     │      CHANNELS, история, PRESENCE                 │
     │◄─────────────────────────────────────────────────┤
```

* Режим `AUTH_PROOF` — основной: пароль не покидает машину игрока вообще.
  Требует, чтобы скриптовый слой отдал ArenaLink `sha256(пароль)`. Если
  пароли лежат в bcrypt и пересчитать proof нельзя, сервер сам присылает
  в `CHALLENGE` режим `AUTH_PLAIN`, и пароль идёт по каналу **ровно так же,
  как при обычном входе в игру по RakNet** — не хуже существующего, но
  и не лучше; в документации это надо написать честно.
* Режим `AUTH_CODE` — первая привязка без пароля: в игре `/chatlink` даёт
  шестизначный код на 5 минут, одноразовый.
* Перебор: 5 попыток с адреса → блок на 5 минут (`throttleAuth`).
* Пароль не сохраняется никогда: в `launcher.cfg` лежит только последнее имя.
  Автовхода по сохранённому паролю нет намеренно.

**Окно входа.** Пока не авторизован — карточка по центру: «Имя персонажа»,
«Пароль», кнопка «Войти» и вторая кнопка «Войти по коду из игры».
Регистрации нет; под полями текст: персонаж создаётся только в игре.
Ошибка `FAIL_NO_ACCOUNT` показывается прямым текстом: «Персонаж не найден.
Зайдите на сервер и создайте его в игре».

### A3. Цвет ника и уровень — как в игре

Источники уже есть: цвет — `customVariables.chatColor` + палитра из
`@@AMP_COLOR@@`, уровень — то же, что уходит в `@@AMP_PLAYERS@@`.

* В протоколе цвет — `u32` `0x00RRGGBB` (`ArenaLink::colorFromHex` берёт
  `#RRGGBB` из палитры сервера), уровень — `u16`.
* Уровень и цвет пишутся **снимком в само сообщение** (`Message::level`,
  `Message::color`). Это принципиально: иначе вся история перекрашивается,
  когда игрок сменил цвет через `/chatcolor` или взял уровень.
* Живой профиль обновляется `PRESENCE_DELTA` — ник в списке игроков
  перекрашивается сразу, без переспрашивания.
* В Qt рендер через `QTextBrowser`: бейдж уровня + ник цветом + время.
  Текст — только через `toHtmlEscaped()`, цвет — только после проверки
  регуляркой `^#[0-9A-Fa-f]{6}$`. Сервер здесь не доверенный источник разметки.

### A4. Каналы и зеркало внутриигрового чата

Каналы задаёт сервер (`LinkServer::start`), по умолчанию:

| id | Название | Флаги |
|---|---|---|
| 1 | Общий | `WRITABLE` + `MIRRORS_GAME` |
| 2 | Поиск группы | `WRITABLE` |
| 3 | Торговля | `WRITABLE` |
| 4 | Объявления | только админы |

`MIRRORS_GAME` — канал двусторонне связан с внутриигровым чатом: написанное
в лаунчере уходит в игру через `pushToGameChat`, написанное в игре приходит
в лаунчер через `publishFromGame` с флагом `MESSAGE_FROM_GAME` (в ленте
помечено «из игры», в списке каналов — значком `↔`).

> Это допущение. Если зеркало не нужно — снять флаг у канала 1, всё остальное
> не меняется.

### A5. Хранилище

Никакой БД: кольцо последних `historyPerChannel` (500) сообщений в памяти
плюс дописываемый `server/data/chat/<id>.jsonl`. При старте читается хвост
файла. Ноль новых зависимостей, история переживает перезапуск, файл можно
листать глазами и грепать.

### A6. Android

`ChatActivity` + `chat/ArenaLinkClient.kt` — тот же протокол, тот же
`proof`, `RecyclerView` вместо `QTextBrowser`. Цвет — `ForegroundColorSpan`,
бейдж уровня — `TextView` с `GradientDrawable`. Кнопка входа — в нижней
панели U024h.

## 3. Часть B — голос

### B1. Состояния коммутатора

```
      ┌────────┐  вход в чат   ┌────────┐   Играть     ┌──────────┐
      │  OFF   ├──────────────►│ LOBBY  ├─────────────►│ HANDOFF  │
      └────────┘               └────────┘              └────┬─────┘
           ▲                       ▲                        │ пришёл тикет
           │ выключен в панели     │ выход из игры          ▼
           │                       └──────────────────┬─────────┐
           └──────────────────────────────────────────┤ INGAME  │
                                                      └─────────┘
```

* **LOBBY** — та же сессия ArenaVoice, только `scope = 0`: сервер не применяет
  ни дистанцию, ни панораму, все слышат всех. Отдельного стека для лобби нет.
* **HANDOFF** — нажата «Играть». Коммутатор **сразу шлёт `BYE`** и выходит
  из общей комнаты, но микрофон не отпускает (на Android иначе пришлось бы
  пересоздавать foreground service). Ждёт тикет игровой сессии.
* **INGAME** — общая комната недоступна вообще, работает только proximity.
  Групповая «рация» (`CHANNEL_GROUP`) остаётся и выключается флагом
  `groupRadio`.
* Выход из игры → LOBBY, но **без автовхода** в общую комнату: показывается
  кнопка «Вернуться в комнату», чтобы игрок не оказался в открытом эфире
  неожиданно для себя.

> Уточнить: «голос из общей комнаты в команде убрать» прочитано как
> «в игре общая комната выключается, остаётся proximity + опциональная
> групповая рация». Если рацию тоже убрать — `groupRadio = false`.

### B2. Voice-сервер

Отдельный поток в `tes3mp-server`, свой UDP-сокет:

```ini
[Voice]
enabled = true
port = 0            ; 0 = игровой порт + 1
mode = client       ; client = сервер считает коэффициенты, клиент сводит
                    ; server = сервер сводит микс (для слабых устройств)
sayRangeMeters = 20
whisperRangeMeters = 5
shoutRangeMeters = 50
rolloff = 1.6
requireSameCell = true
interiorIsolation = true
maxAudibleSpeakers = 6
maxBitrateKbps = 24
ticketTtlSeconds = 120
```

**Почему `mode = client` по умолчанию.** Сервер в обоих режимах остаётся
авторитетом: только он решает, кто кого слышит, и считает усиление и азимут.
Разница — кто складывает сигналы:

| | `mode = client` | `mode = server` |
|---|---|---|
| CPU сервера на 30 игроков | ~0 (пересылка байтов) | 30 декодов + 30 кодировок Opus, ~1.5–2 ядра |
| Качество | лучше (нет двойного кодирования) | заметно хуже |
| HRTF, свой микс, ползунки громкости | есть | нет |
| Трафик клиента | до 6 потоков ≈ 90 кбит/с | 1 поток ≈ 24 кбит/с |
| Слабый Android | тяжелее | легче |

Тик 20 мс, синхронно с фреймом Opus: позиции берутся из снимка
`publishSnapshot()`, который публикует игровой цикл. Голосовой поток
**не держит** игровые структуры под блокировкой.

### B3. Протокол ArenaVoice (AVX1)

Заголовок 12 байт, big-endian, датаграмма ≤ 1200 байт.

| Тип | Направление | Нагрузка |
|---|---|---|
| `0x01 HELLO` | c→s | ticket[16], protocol u16, caps u16, ник |
| `0x02 WELCOME` | s→c | ssrc u32, tickMs u16, mode u8, maxSpeakers u8, rangeUnits u32 |
| `0x03 REJECT` | s→c | причина u8 (тикет, бан, переполнение, версия, лимит) |
| `0x10 AUDIO_UP` | c→s | seq u16, ts u32, канал u8, флаги u8, opus |
| `0x11 AUDIO_DOWN` | s→c | ssrc u32, seq u16, ts u32, gain u8, азимут i16, дистанция u16, флаги u8, opus |
| `0x12 MIXDOWN` | s→c | seq u16, ts u32, opus (только `mode = server`) |
| `0x20 STATE` | c→s | позиция i32×3, yaw/pitch i16, ячейка u32, канал u8, ptt u8, muted u8 |
| `0x21 PEERS` | s→c | кто сейчас говорит и с какой громкостью |
| `0x30/0x31 PING/PONG` | обе | ts u32 |
| `0x40 CONTROL` | s→c | op u8 (mute/kick/range/mode/тикет протух), arg u32 |

Правила:

* Opus 48 кГц mono, 20 мс, VBR 16–24 кбит/с, inband FEC и DTX включены,
  PLC на приёме.
* `AUDIO_UP` идёт только пока нажат PTT или открыт VAD; пауза > 400 мс →
  пакет с флагом `EOS`, приёмник гасит источник.
* `STATE` — 10 Гц. Позиция в юнитах, `1 м = 69.99 юнита` (64 юнита = 1 ярд).
  Сервер **не доверяет** позиции из `STATE`: она берётся из игрового
  состояния, клиентская нужна только для интерполяции поворота головы.
  Иначе клиент смог бы «телепортировать» свой голос.
* Тикет: 16 случайных байт, выдаёт сервер (через ArenaLink или при входе
  в мир), TTL 120 с, одноразовый. Адрес привязывается при `HELLO`; смена
  сети требует нового `HELLO` — для телефона это норма.
* Анти-флуд: ≤ 60 `AUDIO_UP`/с на сессию, ≤ 4 `HELLO`/мин с адреса.

### B4. Позиционная математика

```
K = 69.99 юнита на метр           // 64 юнита = 1 ярд = 0.9144 м
dMin = 2 м (140 юнитов)           // ближняя зона, gain = 1
dMax = радиус канала              // шёпот 5 / обычный 20 / крик 50 м

gain = 0                                        , d >= dMax
gain = 1                                        , d <= dMin
gain = ((dMax - d) / (dMax - dMin)) ^ rolloff   , иначе
```

Линейный закон с показателем 1.6 выбран вместо `dMin/d` намеренно: обратная
пропорция даёт резкий обрыв у границы и «шёпот из ниоткуда». `rolloff`
вынесен в конфиг: 1.0 — ровнее, 2.0 — «слышно только вплотную».

Азимут (левое/правое ухо):

```
rel     = позиция говорящего - позиция слушателя
azimuth = atan2(rel.x, rel.y) - yaw слушателя   // Морровинд: +X восток, +Y север
```

Дальше два пути:

* **ПК (OpenAL, рекомендуется):** панораму руками не считаем. На каждый ssrc —
  свой `alSource`, `AL_SOURCE_RELATIVE = AL_TRUE`, позиция
  `(sin(az)·d, 0, −cos(az)·d)` в метрах, `AL_ROLLOFF_FACTOR = 0` (затухание
  уже посчитал сервер), `AL_GAIN = gain`. Панорама, расстояние и HRTF —
  на OpenAL Soft. `hrtf enable` берём из `settings.cfg [Sound]`, чтобы
  совпадало с игрой.
* **Android / ручной микс:** равномощная панорама
  `L = gain·cos((pan+1)·π/4)`, `R = gain·sin((pan+1)·π/4)`, `pan = sin(az)`.

Сглаживание обязательно: `gain` и азимут интерполируются за 60–80 мс,
иначе на быстром повороте камеры слышны щелчки.

Правила слышимости (считает сервер):

1. Интерьер ↔ экстерьер — не слышно.
2. Разные интерьеры — не слышно (`interiorIsolation`).
3. Экстерьер — по дистанции независимо от ячейки: границы ячеек не должны
   резать звук.
4. Один интерьер — по дистанции, радиус ×0.8 (стены).
5. Скрытый (невидимость, хамелеон) — слышно, но с флагом `ANON`: ник не
   показывается, в HUD «???».
6. Не более `maxAudibleSpeakers` ближайших.

Каналы речи берутся из существующих: голос следует за текстовым каналом
(шёпот/обычный/крик), отдельной настройки не заводим.

### B5. Коммутатор в лаунчере

Модуль `launcher/voice/`:

* `VoiceCommutator` — автомат состояний, владеет сокетами (UDP к серверу +
  loopback-мост к движку).
* Захват: `alcCaptureOpenDevice` — OpenAL уже линкуется, новых зависимостей нет.
  48 кГц mono s16, окно 960 сэмплов.
* Кодек: **libopus** — единственная новая зависимость проекта (≈300 КБ),
  нужна только лаунчеру и Android. Серверу в режиме `mode = client` не нужна.
* Воспроизведение: пул `alSource` + адаптивный джиттер-буфер 40–120 мс.
* Обработка микрофона: DC-фильтр → шумовой гейт (−45 дБ, атака 5 мс, спад
  200 мс) → AGC → Opus. Полноценный WebRTC-APM не тянем.
* `VoicePanel` — управление на странице чата: включение, режим (рация/по
  голосу), клавиша, устройства ввода и вывода (списки из `openalutil.cpp`),
  чувствительность, громкость, mute, строка состояния и «кто говорит».
  Панель остаётся доступной **после запуска игры** — в этом и смысл того,
  что лаунчер не закрывается.

### B6. Мост движок ↔ коммутатор

Лаунчер перед запуском игры дописывает в `tes3mp-client.cfg`:

```ini
[Voice]
bridgePort  = 51234       ; выбран лаунчером
bridgeToken = 32-hex      ; одноразовый, на один запуск
```

Движок (`VoiceBridge`, рядом с существующим `VoiceChat`):

* 10 Гц шлёт на `127.0.0.1:bridgePort` состояние слушателя (позиция,
  yaw/pitch, ячейка, канал, PTT, mute) и, один раз, голосовой тикет;
* принимает список говорящих и отдаёт его в `GUIChat`/HUD;
* нет ответа 3 с → коммутатора нет: либо молчим, либо включаем встроенный
  `VoiceChat` как запасной путь (по настройке).

Существующий `VoiceChat` **не удаляем**: он остаётся fallback для запуска
клиента без лаунчера. Но пока мост жив, он обязан быть в режиме «только
индикация» и не открывать устройство захвата — иначе два процесса подерутся
за микрофон.

`Networking::isVoiceEnabled()` перестаёт возвращать жёсткий `false` и
привязывается к `[Voice] enabled`; ретрансляция старого образца через
игровой RakNet остаётся выключенной навсегда — голос ходит только по
ArenaVoice.

## 4. Часть C — Android

### C1. Права

```xml
<uses-permission android:name="android.permission.RECORD_AUDIO"/>
<uses-permission android:name="android.permission.MODIFY_AUDIO_SETTINGS"/>
<uses-permission android:name="android.permission.FOREGROUND_SERVICE"/>
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_MICROPHONE"/>   <!-- API 34+ -->
<uses-permission android:name="android.permission.POST_NOTIFICATIONS"/>              <!-- API 33+ -->
<uses-permission android:name="android.permission.BLUETOOTH_CONNECT"
                 android:usesPermissionFlags="neverForLocation"/>                    <!-- API 31+ -->

<service android:name="voice.VoiceService"
         android:exported="false"
         android:foregroundServiceType="microphone"
         android:stopWithTask="true"/>
```

Три ловушки, которые ломают такие сервисы:

1. **Android 14 (API 34): FGS типа `microphone` нельзя стартовать из фона.**
   Сервис обязан запускаться, пока `MainActivity` на переднем плане — при
   включении тумблера или в момент нажатия «Играть», **до**
   `startActivity(GameActivity)`. Старт из `GameActivity.onCreate()` даёт
   `ForegroundServiceStartNotAllowedException` на части устройств.
2. **Android 13 (API 33): без `POST_NOTIFICATIONS` уведомление не видно** —
   сервис живёт, а игрок не понимает, почему горит индикатор микрофона.
   Просить вместе с `RECORD_AUDIO`, одной цепочкой.
3. **Android 12L+ показывает индикатор микрофона** — убрать нельзя. В
   уведомлении делаем кнопки «Заглушить» и «Выключить голос», чтобы
   индикатор был объясним.

Отказ в правах → тумблер выключается и остаётся выключенным, текст «Голос
выключен: нет доступа к микрофону». Отказ с «не спрашивать» → кнопка ведёт
в `ACTION_APPLICATION_DETAILS_SETTINGS`.

### C2. Аудио-режимы

| Задача | Решение | Почему |
|---|---|---|
| Захват | `AudioRecord`, source `VOICE_COMMUNICATION`, 48 кГц mono, буфер 4×20 мс | системные AEC/NS/AGC |
| Эхо | `AcousticEchoCanceler` + `NoiseSuppressor`, если `isAvailable()` | иначе динамик возвращает эхо в канал |
| Вывод | `AudioTrack` 48 кГц stereo, `USAGE_GAME`, `CONTENT_TYPE_SPEECH`, low latency | `USAGE_VOICE_COMMUNICATION` душит игровой звук |
| Режим | оставляем `MODE_NORMAL`, **не** `MODE_IN_COMMUNICATION` | последний уводит вывод в разговорный динамик на части прошивок |
| BT-гарнитура | `setCommunicationDevice()` (API 31+) | иначе микрофон берётся встроенный |
| Кодек | libopus через JNI | `MediaCodec` даёт Opus-декодер почти везде, кодер — нет |

Слабые устройства (`availableProcessors() <= 4` или `pref_voice_low_power`):
коммутатор просит `mode = server` и получает один `MIXDOWN` без панорамы
по ушам; дистанция сохраняется.

### C3. UI

Категория «Голосовой чат» в `settings.xml`: включение (по умолчанию
**выключено**), режим передачи, чувствительность, громкость, экономный
режим, кнопка «Разрешения». В игре — кнопка микрофона в наборе экранных
контролов (`ConfigureControls`, перетаскиваемая): короткое нажатие
mute/unmute, удержание PTT.

### C4. Батарея и фон

* `MainActivity` в фоне, игра не запущена → захват на паузу через 15 с,
  сокет живой.
* `GameActivity` свёрнута → захват и воспроизведение на паузу немедленно,
  `STATE` с `muted = 1`.
* `stopWithTask = true` — смахнули приложение, сервис умер.
* Wake lock не берём: FGS типа `microphone` и так держит аудио-путь.

## 5. Часть D — безопасность

| Риск | Мера |
|---|---|
| Пароль в сети | `AUTH_PROOF`: по сети идёт HMAC от nonce, пароль не покидает машину |
| Пароль на диске | не сохраняется нигде: ни в `launcher.cfg`, ни в `SharedPreferences` |
| Перебор пароля | 5 попыток с адреса → блок 5 минут, отдельный счётчик на имя |
| Подмена голосовой личности | одноразовый тикет от сервера, привязка к сессии и адресу |
| Прослушивание чужих | сервер сам решает, кому слать: клиент физически не получает пакеты дальних игроков |
| Определение позиции по трафику | дальние координаты не отдаются; только азимут и дистанция слышимых, `ANON` для скрытых |
| Флуд в чате | 30 сообщений в минуту на клиента, 4 соединения с адреса, 128 всего |
| Флуд в голосе | лимит кадров, отдельный сокет — игровой трафик не страдает |
| Модерация | бан и mute из игры действуют на чат и голос немедленно (`disconnectUser`, `CONTROL_MUTE`) |
| Битый кадр | чужая сигнатура или длина > 16 КБ → соединение закрывается, а не ищется синхронизация в потоке |
| Запись разговоров | не ведётся и не предусмотрена — заявить явно в README проекта |

| Патч | Содержимое | Проверяется отдельно |
|---|---|---|
| **U025a** | `arenastream.hpp`, `arenalink.hpp`, `LinkServer` в сервере, `/chatlink` | telnet/скриптом: вход игровым аккаунтом отдаёт уровень и цвет |

## 8. Часть G — что проверить руками

1. Сборка Qt-страницы и линковка libopus на MSVC/MinGW.
2. `alcCaptureOpenDevice` на устройствах с несколькими микрофонами.
3. FGS `microphone` на Android 14/15: реальный старт из `MainActivity` и
   переживание перехода в `GameActivity`.
4. Переключение Wi-Fi → LTE: новый `HELLO` тем же тикетом, пока TTL не истёк.
5. Двойной захват микрофона: старый `VoiceChat` не должен открывать
   устройство, когда мост жив.
6. `MODE_NORMAL` против `MODE_IN_COMMUNICATION` на нескольких прошивках.
7. Нагрузка сервера на 30 говорящих: тик 20 мс не должен просаживать
   игровой цикл — копия позиций раз в тик, без долгой блокировки `Players`.
8. Поведение чата при падении ArenaLink: игра обязана продолжать работать
   так, будто чата нет вообще.

## 9. Открытые вопросы

1. Групповая рация в игре — оставляем (текущее допущение) или убираем вместе
   с общей комнатой?
2. Зеркало внутриигрового чата в канале «Общий» — нужно или чат лаунчера
   полностью отдельный?

   хватает, это примерно один день работы.

   «обычный» стоит опустить до 12–15 м.

6. Хранить ли историю чата вообще, или лента живёт только в памяти до
   перезапуска сервера?
