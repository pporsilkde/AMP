
## U009: HTTPS на Windows без OpenSSL

По фактическому `Update.log` нативный U008 worker запускался и читал `build.ini`, но Qt Network завершал запрос `check.ini` ошибкой `TLS initialization failed`. Это означает отсутствие/несовместимость runtime OpenSSL у конкретной Qt 5 Windows-сборки, а не ошибку `check.ini`.

В U009 Windows-загрузки (`check.ini`, клиент и контент) переведены на системный **WinHTTP**. TLS, проверка сертификата и доверенное хранилище предоставляет Windows; `arena-updater.exe` больше не линкуется с `Qt5::Network` на Windows и не требует `libssl`/`libcrypto` для обновлений. Linux остаётся на Qt Network. В `Update.log` Windows-загрузка помечается `transport=winhttp`. Частичный `.download` удаляется при сетевой ошибке, неполной загрузке или неверном SHA-256.

# U006: нативный Qt/C++ обновлятор; исправления U005 и Android сохранены

Патч подготовлен относительно **GitHub(8).zip**, переданного 10.09.2026. Поддерживаемые готовые пакеты: Windows x64, Linux x86_64 / Steam Deck и Android arm64 из приложенных проектов. Это исходники для пересборки, не готовые EXE/APK.

## U007: видимое окно установки

При реальной установке (`update`, `prepare`, `apply`) нативный updater теперь принудительно
показывает отдельное окно поверх закрывающегося launcher: текущий этап, прогресс загрузки,
распаковки и установки, объём данных и имя текущего файла. На Windows окно дополнительно
поднимается нативным WinAPI и отмечается в панели задач. Проверка `check` остаётся тихой.


## U006 — обновлятор больше не Python/PyInstaller

Windows/Linux worker полностью перенесён в `apps/launcher/updater/arena_updater.cpp` и собирается CMake как обычный Qt 5/C++ executable `arena-updater`. В release workflow удалены установка Python и сборка worker через PyInstaller. Python на компьютере игрока для обновления больше не используется.

Отдельный процесс сохранён специально: после нажатия «Обновить» старый `arenamp-launcher` закрывается, а updater продолжает работать и может заменить сам лаунчер, `arena-updater.exe` и DLL. На Windows перед закрытием лаунчера updater временно копируется в staging вместе с Qt DLL и plugin-каталогами (`platforms`, `styles` и др.); поэтому замена файлов рабочей папки не блокирует сам установщик. Обычная проверка `check.ini` staging не создаёт.

У updater теперь собственное Qt-окно: текущая стадия, строка состояния, прогресс загрузки с объёмом данных, прогресс распаковки/установки, кнопка отмены до начала транзакционной замены и раскрываемые подробности. Все этапы одновременно пишутся в `Update.log`.

Сохранены проверки SHA-256, ZIP/ZIP64 и TAR.GZ, ограничения размера/числа файлов, защита от path traversal и опасных объектов архива, проверка свободного места, блокировка параллельной установки, журнал транзакции, rollback и восстановление после прерванного обновления. Коды `check` остаются совместимыми с U005: `0` — актуально/offline, `10` — обновление доступно, `20` — восстановление/ошибка требует внимания.

`arena-updater --self-test` запускается непосредственно из Windows/Linux GitHub Actions после CMake install. Это проверяет уже собранный нативный бинарник и не требует Qt platform plugin для self-test.

Переход с PyInstaller убирает типичный источник ложных детектов Chrome/SmartScreen, но сам по себе не создаёт репутацию нового EXE. Для публичных Windows-релизов дополнительно рекомендуется Authenticode-подпись `arena-updater.exe`, `arenamp-launcher.exe` и основного клиента одним постоянным сертификатом.

Если U006 накладывается **поверх уже установленного U005 исходного дерева**, удалите старые `apps/launcher/updater/arena_updater.py` и `apps/launcher/updater/test_updater.py`: они больше не входят в сборку и в чистой базе U006 отсутствуют.

## U005 — причина подтверждена присланным Update.log


Worker успешно прочитал check.ini: HTTP 200, локальные version/build — 00001/00001, удалённые — 00002/00003. После `available` и завершения проверки с кодом 10 лаунчер записал `check_cancelled`. Ошибки сети или сравнения версий в этом логе нет; скачивание update.zip и движка ещё не запускалось.

В общем коде Windows/Linux программный `progress.close()` испускал сигнал `canceled()`, который сбрасывал уже найденное обновление. Теперь на время программного закрытия используется `QSignalBlocker`; настоящая отмена пользователем сохраняется. В конце проверки Update.log содержит `check_finished` с `cancelled=0/1` и `button=Update/Play`.

Исправлен исходник `apps/launcher/updatecontroller.cpp`: требуется пересборка **arenamp-launcher**, а не только отдельного обновлятора. Все изменения U004 и Android сохранены.

В `apps/launcher/updater/qt-tests/` добавлен отдельный тест настоящего контроллера и окна Qt с процессом-имитатором. Он проверяет пять сценариев: наличие обоих обновлений, код 10 без вывода, равные версии, недоступный check.ini и реальную отмену. Тест выполняется в существующем Linux workflow до сборки движка. Локально скомпилирован C++ имитатор и проверены четыре его режима; запуск Qt-теста здесь недоступен без Qt SDK.

В U004 исправлен Android-лаунчер: endpoint из `build.ini` импортируется синхронно до показа настроек и перед запуском игры, при `complete=true` поля основного IP/порта скрываются, а поля альтернативного сервера раскрываются только после установки флажка. После скачивания APK сохранённый пакет не теряется: повторная установка возможна после выдачи разрешения Android, а отмена установки больше не проходит без сообщения.

Также устранены пропуск проверки при `--arena-update-resume`, зависимость фонового обновлятора от консольного stdout и перезапуск нового лаунчера до закрытия старого. На Android значения обновляются в самих объектах настроек, поэтому прежнее `127.0.0.1` не остаётся в поле после импорта. Добавлен постоянный `Update.log` на обеих платформах. Приложенный пользователем U003 проверен: его SHA-256 совпадает с предыдущим выданным U003; этот архив включает все его изменения.

## Два независимых счётчика

Локальный `build.ini` рядом с выбранной Data Files:

```ini
[Build]
format=1
name="project NIRN 2.0"
data-path="Data files"
complete=true
version=00001
build=00001
url="t.me/arena_mp"
url_check="mro1.myarena.site/build/check.ini"
url_update="mro1.myarena.site/build/update.zip"
url_win="mro1.myarena.site/build/ArenaMP-Windows-x64-main.zip"
url_linux="mro1.myarena.site/build/ArenaMP-Linux-x86_64-SteamDeck-main.tar.gz"
url_android="mro1.myarena.site/build/ArenaMP-arm64-client-server.apk"

[Server]
address="178.20.47.31"
port="25565"
use_alt_server=false
alt_adress=""
alt_port="25565"
```

Удалённый `check.ini`, без обязательной секции:

```ini
version=00002
build=00003
```

| Ключ | Назначение |
|---|---|
| `format` | Формат manifest; остаётся `1` |
| `version` | Версия контента Data Files |
| `build` | Версия установленного движка/клиента |
| `url_check` | Адрес check.ini |
| `url_update` | Контент ZIP для Data Files |
| `url_win` | Windows ZIP с клиентом и лаунчером |
| `url_linux` | Linux TAR.GZ или ZIP с клиентом и лаунчером |
| `url_android` | APK с тем же applicationId и ключом подписи |
| `url` | Кнопка ссылки на сайт/Telegram сервера |

Числа сравниваются как десятичные: `00010 > 00009`, `00001 = 1`. Ведущие нули сохраняются. Версии движка не связаны с TES3MP protocol, commit или resources/version. Старое ошибочное использование `version` вместо `format` исправлено в обоих парсерах.

Адреса без схемы автоматически получают `https://`. Если сервер действительно работает только по HTTP, следует явно указать `http://`; автоматического понижения с HTTPS на HTTP нет.

## Запуск и отсутствие сети

При открытии лаунчера выполняется только лёгкая проверка check.ini. Если счётчик выше локального, кнопки «Играть» меняются на «Обновить». Оба счётчика могут увеличиться одновременно; обычная кнопка «Играть» в этом сценарии не вызывает обновлятор.

Недоступный check.ini, HTTP-ошибка, сетевой таймаут или некорректный check.ini оставляют обычную кнопку «Играть»: установленная версия запускается штатным путём. На ПК проверка ограничена общим таймаутом 12 секунд, на Android используются короткие сетевые таймауты.

Если обновление уже найдено, но его архив повреждён или замена не удалась, новая версия не отмечается как установленная. Supervisor снова открывает лаунчер; кнопка «Обновить» остаётся доступной для повторной попытки, а при отсутствии check.ini пользователь всё равно может нажать обычную «Играть». Если восстановление прерванной транзакции не удалось, игра не запускается поверх частично заменённых файлов.

## Формат пакета контента

В корне update.zip должны находиться **файлы и каталоги, предназначенные для Data Files**:

```text
Textures/...
Meshes/...
Sound/...
Nirn_Core.ESP
Nirn_Pack_001.bsa
```

Также принимается единственная внешняя папка `Data Files/`. Смешанный архив с `Data Files/`, `server/`, `build.ini` рядом не является пакетом контента этой системы. Настройки клиента и build.ini через update.zip не заменяются.

Пакет распаковывается именно в реально выбранный каталог Data Files, в том числе если его регистр/название отличается. Порядок существующих content/groundcover/archive остаётся прежним. Новые плагины автоматически в список не добавляются.

`update.zip` должен содержать накопительные изменения для всех поддерживаемых старых версий либо полный актуальный контент. Иначе пользователь, пропустивший несколько выпусков, может не получить промежуточные файлы. Удаление контентных файлов отдельным списком в этом протоколе не предусмотрено.

Архив сначала полностью скачивается и проверяется, затем распаковывается во временный каталог. Защищены выход за пределы каталога, абсолютные пути и неоднозначные имена. Версия контента записывается последней, в одной транзакции с заменой файлов. При ошибке восстанавливаются прежние файлы; журнал позволяет повторить восстановление после прерывания процесса.

Дополнительно check.ini может содержать SHA-256 пакетов:

```ini
sha256_update=<64 hex characters>
sha256_win=<64 hex characters>
sha256_linux=<64 hex characters>
sha256_android=<64 hex characters>
```

Поля необязательны для совместимости с вашим check.ini. Если поле присутствует, несовпадение хеша запрещает установку.

## Обновлятор ПК

GitHub Actions собирает `arena-updater.exe` для Windows и `arena-updater` для Linux непосредственно из C++/Qt и кладёт его рядом с arenamp-launcher. Python-worker и резервный запуск `.py` удалены: если нативного helper нет, лаунчер сообщает о неполной установке, а не пытается искать Python.

При открытии лаунчера выполняется только лёгкая проверка check.ini. Если найдено повышение version или build, кнопка «Играть» меняется на «Обновить». Обычная кнопка «Играть» больше не запускает обновлятор и возвращается к штатному запуску tes3mp.

После нажатия «Обновить» лаунчер закрывается, а отдельный supervisor ждёт завершения его процесса и выполняет скачивание, подготовку и замену файлов. Затем он запускает новый arenamp-launcher. Лаунчер снова сравнивает фактический build.ini с check.ini: «Играть» появляется при равных версиях или недоступной проверке, «Обновить» — если есть ещё не установленное обновление. Сам аргумент `--arena-update-resume` больше не скрывает обновления.

При обычном нажатии «Играть» адрес/порт передаются непосредственно `tes3mp` штатным путём. Обновлятор не запускает игру. На Linux завершившийся процесс-зомби считается закрытым, чтобы транзакция не ждала лишние 120 секунд.

Для готовой Windows-сборки `arena-updater.exe` должен лежать рядом с `arenamp-launcher.exe`. Если запуск обновлятора по кнопке не удался, лаунчер показывает причину и остаётся открытым; после исправления комплекта можно снова нажать «Обновить».

Windows-пакет должен содержать `arenamp-launcher.exe` и `tes3mp.exe` в корне. Linux-пакет — штатный переносимый набор с `arenamp-launcher`, `tes3mp`, библиотеками и ресурсами; поддерживаются wrapper-файлы `.x86_64`. Допускается одна общая внешняя папка релиза. Символические ссылки на библиотеки внутри TAR.GZ превращаются в обычные копии соответствующих файлов; внешние и циклические ссылки запрещены.

При обновлении клиента сохраняются `server/`, `userdata/`, `saves/`, `screenshots/`, Data Files и пользовательские CFG/INI. Файл `requiredDataFiles.json` (манифест, созданный кнопкой «Обновить хеши») дополнительно защищён по имени: пакет движка не заменяет его ни в `server/data/`, ни по любому другому пути внутри архива. Сам `build.ini` обновляется только по счётчикам после успеха. Настройки выбранного сервера не берутся из релизного архива. Запущенные экземпляры игры/сервера из этой установки нужно закрыть перед заменой файлов; проверка check.ini при этом всё равно выполняется.

Рабочие папки должны быть доступны текущему пользователю для записи. Автоматического запуска от администратора нет. Этот выпуск настраивает распространение обновлятора в Windows/Linux workflow; автоматическая замена macOS .app в него не входит, URL для macOS в предоставленном build.ini отсутствует.

После завершения мастера создаётся ярлык arenamp-launcher на рабочем столе под именем сервера из `name` — в вашем примере **project NIRN 2.0**. В Windows это `.lnk`, в Linux `.desktop`. Существующий одноимённый ярлык не удаляется.

## APK и постоянная подпись

После скачивания Android проверяет, что файл является APK, его package/applicationId совпадает с установленным приложением, подпись совпадает и versionCode увеличен. Затем открывается системный установщик через FileProvider. Если нужно разрешить установку из этого источника, сначала открывается соответствующая системная настройка, затем установка продолжается.

Установка требует действия пользователя в системном интерфейсе Android. Отмена не повышает `build`. Загруженный подходящий APK сохраняется для повторной попытки. При следующем запуске сверяется фактический versionCode установленного приложения; lastUpdateTime остаётся запасной проверкой для состояния, созданного старой версией обновлятора. Только после подтверждённой установки и развёртывания ресурсов повышается локальный build. Счётчик записывается через временный файл, без регенерации серверных адресов и списка плагинов.

На Android проверка при открытии лаунчера и установка разделены. Нижняя кнопка подписана «Играть» или «Обновить». Обычная «Играть» не вызывает сетевую проверку и идёт штатным путём запуска клиента; кнопка «Обновить» показывает прогресс и затем открывает системную установку APK. Android-лаунчер остаётся владельцем окна прогресса до передачи APK системному установщику.

Для рабочих релизов настройте секреты Android-репозитория:

- `ARENA_ANDROID_KEYSTORE_BASE64` — существующий keystore, подписывающий ваши APK, в Base64;
- `ARENA_ANDROID_STORE_PASSWORD`;
- `ARENA_ANDROID_KEY_ALIAS`;
- `ARENA_ANDROID_KEY_PASSWORD`.

**Нужен именно прежний ключ.** Создание нового ключа не позволит обновлять APK, ранее подписанный другим ключом. Если исходный ключ старого debug APK утерян, исправить его подпись данным патчем невозможно.

При отсутствии release-секретов workflow сохраняет debug.keystore в кэше для последующих тестовых сборок. Это не замена резервной копии release-ключа: очистка кэша потеряет тестовую подпись. Для CI versionCode автоматически устанавливается в `100000 + GITHUB_RUN_NUMBER`; для локальной сборки можно задать `ARENA_ANDROID_VERSION_CODE`, иначе используется `48`. При смене workflow/счётчика необходимо сохранить увеличение относительно уже опубликованного APK.

## Обновление assets после установки APK

Упакованные assets внутри приложения меняются вместе с APK. Дополнительно обновляются их ранее извлечённые рабочие копии:

- `libopenmw/resources` → внутренний каталог `files/resources`;
- `libopenmw/openmw` → внутренний каталог стандартных настроек `files/config`;
- серверные scripts/lib, resources и стандартный серверный CFG из `arenamp-server` → управляемые каталоги встроенного сервера.

Решение о повторном развёртывании принимается по отпечатку фактического списка assets в APK, CRC и размеров файлов. Это не зависит от сетевого resources/version. Даже если сетевые protocol/commit не изменились, обновлённые assets будут замечены.

Клиентские ресурсы подготавливаются до запуска игры; серверные — перед использованием встроенного сервера. Сначала создаётся полная временная копия, затем управляемые каталоги заменяются с журналом отката. Файлы, удалённые из нового набора ресурсов, исчезают из старой рабочей копии. Маркер новой версии ставится последним. Ошибки чтения/записи assets больше не скрываются.

Пользовательский каталог конфигурации, Data Files, сохранения, серверные player/cell/world/custom данные и постоянный `server-config.lua` сохраняются. Новые стандартные серверные данные добавляются только в отсутствующие файлы. Ресурсы, которые приложение читает непосредственно из APK, не требуют отдельной распаковки.

## Альтернативный сервер и ссылка

Флажок «Подключиться к другому серверу» открывает отдельные поля адреса и порта. Они сохраняются как `alt_adress` и `alt_port`; также принимается корректное написание `alt_address`. Выбор сохраняется в `use_alt_server`.

При `complete=true` основной `address="178.20.47.31"` и `port="25565"` остаются неизменными. Снятие флажка возвращает подключение к основному серверу. Локальный host-режим и альтернативное подключение взаимоисключаются. Пустой адрес или порт вне 1–65535 не допускаются.

На ПК кнопка «Сайт сервера» открывает `url`. На Android для этой ссылки используется существующая кнопка с глобусом; `t.me/arena_mp` преобразуется в `https://t.me/arena_mp`.

## Публикация обновления

1. Пересобрать и проверить нужный Windows/Linux пакет или APK; при APK сохранить ключ подписи и увеличить versionCode.
2. Подготовить накопительный update.zip, если меняется контент.
3. Загрузить пакеты на сервер по URL из build.ini. При необходимости посчитать их SHA-256.
4. **Последним** опубликовать check.ini с увеличенным version и/или build. Это исключает ситуацию, когда лаунчер уже видит новую версию, а пакет ещё не загружен.
5. Проверить один клиент со старым номером, обновление самого лаунчера, установку APK, обновление assets и запуск при недоступном check.ini.

## Диагностика через Update.log

Основной путь на ПК и Android — **рядом с фактически выбранным build.ini**. Лог не очищается при каждом открытии лаунчера и не включается в замену файлов из обновления. При размере более 4 МиБ предыдущая часть переносится в `Update.log.old`.

Если основной каталог недоступен для записи, ПК пробует каталог клиента и кэш лаунчера, Android — `Android/data/<applicationId>/files/Update.log`, затем внутренний каталог приложения. В ошибке Android показывается фактический путь. В обычной сборке applicationId — `com.mrzer0x0.arenamp`.

Записываются путь build.ini, локальные и удалённые version/build, URL, решение «Играть/Обновить», байты скачивания, проверка пакетов, распаковка, установка и ошибки со стеком. Android дополнительно записывает импорт и фактический адрес подключения, versionCode APK, запрос разрешения, возврат системного установщика и развёртывание клиентских/серверных assets. ПК записывает запуск helper, его stderr/код завершения, ожидание закрытия старого процесса и повторный запуск лаунчера.

Если ошибка повторится после пересборки с U004, воспроизведите её один раз и пришлите `Update.log` с соответствующей платформы. По нему можно отличить неверный путь build.ini, недоступный HTTPS/HTTP, равные версии, повреждённый архив и отказ установки APK; причина сбоя на конкретном устройстве без этого лога не подтверждена.

Полная компиляция Qt-лаунчера и Android-приложения, создание готовых EXE/APK, реальная системная установка APK и создание ярлыков в Windows/Linux здесь не выполнялись: в среде нет Qt SDK/Android SDK. Добавленные тесты включены в существующие CI-сборки. После наложения исходников следует запустить эти сборки и проверить установку на целевых устройствах.

Справочные требования платформ: [подпись Android-приложений](https://developer.android.com/studio/publish/app-signing), [разрешение на установку APK](https://developer.android.com/reference/android/content/pm/PackageManager#canRequestPackageInstalls()), [FileProvider](https://developer.android.com/reference/androidx/core/content/FileProvider).
